# DeFi catalog workflow

The current catalog source is `data/defi-catalog/catalog.json`. Offline tooling validates this reviewed input and deterministically generates the static TypeScript module consumed by the runtime and `frontend/public/protocols.json` for public download. Runtime authorization does not discover or load source snapshots or plans.

## Lean admission path

### Lifecycle exclusion policy

Do not admit or retain protocols whose team has disbanded or whose project is winding down or shut down. Retired/sunset deployments and explicitly unmaintained legacy integrations are also unsupported, even if their contracts still expose withdrawal functions. There is no exit-only exception. Remove their capabilities from `catalog.json`, regenerate both outputs, and remove their public directory cards; hiding a card or adding warnings is not sufficient. Existing custom IDs cannot restore a removed capability. Keep historical source evidence for audit only; it is not an admission instruction.

As of 2026-10-21, this policy removes 40 capabilities across Nomiswap V1 (team disbanded), Mountain wUSDM (wind-down), Saddle USD (wind-down), mStable savings (deprecated exit-only deployment), Prisma mkUSD StabilityPool (shutdown), Badger legacy Sett (sunset), Nerve 3pool (retired migration/exit-only deployment), and Ramses V1 (legacy support/update cessation). The latter deployment exclusions do not assert shutdown of a successor product or the entire Ramses/Badger ecosystem. Alpaca remains unadmitted. A shutdown notice for another chain alone is not grounds to classify the reviewed deployment as shut down; MDEX's HECO notice does not establish a BSC shutdown.

The dated admission sections below are historical records and are superseded by this exclusion policy and the current `catalog.json`; their former active counts do not describe current support. No catalog maintenance step should reimport their historical `selectedFunctions` wholesale.


Use a contract-first inventory: **chain and exact deployed address → matching ABI → function inventory → capability records → existing catalog workflow**. Establish the chain/address from a reliable deployment source and bind the ABI to that deployment using a reliable ABI source. Where a proxy is involved, match the proxy address and the applicable implementation/interface; record the relevant implementation identity when available. These are inventory evidence, not proof of current runtime bytecode identity, funding, or executable behavior.

Enumerate ABI `function` entries as the callable interface surface. ABI entries do not say whether a function was declared `public` or `external`; either appears as a function. Internal/private functions are not part of this ABI surface. Do not create function capabilities for constructors, `fallback`, or `receive`. Retain `view`/`pure` mutability metadata, without implying that a read endpoint exists. Identify functions by their full canonical signature, not name alone: include canonical tuple component types and array suffixes (for example, `f((address,uint256)[],uint8)`). Overloads are supported when their selectors differ; the manifest rejects selector collisions, not repeated function names.

The capability identity remains the existing chain + exact address + full canonical signature, bound to the fixed ABI fragment and existing catalog ID/schema. Inventory is not automatic activation: ordinary entries can be recorded without requiring full-workflow, market-coverage, liquidity, funding, or financial-safety research as admission prerequisites. Keep security-sensitive functions and opaque multicall/executor surfaces unactivated unless they fit the existing independently required execution controls; give every unactivated entry a specific reason. This is not a new per-function financial-review process.

The inventory helper emits schema-v1 per-function records for manual review; it does not import into or write `catalog.json`. It requires explicit chain, address, protocol, deployment evidence and ABI evidence. Both evidence records carry `sourceRef`, `verifiedAt`, `chainId`, and `address`, and must match the supplied deployment identity. Input is a local JSON file with those fields and the ABI array; run `npm run defi:catalog:inventory -- path/to/input.json`. The helper makes no network/RPC/database calls and writes only drafts to stdout. Drafts and their hierarchy are inactive, provenance is `candidate`, and each function has an explicit review reason. Review/edit selected records and merge them into `data/defi-catalog/catalog.json` manually; never activate an ABI wholesale or write API-key grants. In `capabilityMode: all`, active, unpaused reviewed capabilities may be used subject to all independent gates; `custom` uses exact configured IDs and `custom` with `[]` denies catalog capabilities.

Minimal draft → review → generate/check workflow, from the repository root:

```sh
npm run defi:catalog:generate
npm run defi:catalog:check
```

Optionally run `npm run defi:catalog:diff` to review catalog changes. `generate` updates both the generated runtime module and public JSON; `check` rejects either missing/stale output. `npm run verify:backend` also runs this catalog check, including in CI. Review the diff, generated output and each record before admission. Catalog entries are function metadata, not API-key grants. Profiles are reviewed metadata groupings only.

These commands are offline and make no network, RPC, or database calls. Profiles do not grant capabilities, expand effective permissions, or prove a complete workflow.

Catalog admission records deployment-source and ABI-binding evidence. It does not establish deployed runtime identity, funding, balances, liquidity, successful execution, complete workflows, or financial safety. Preserve canonical ABI decoding, authorization, pause checks, final rechecks, and signing/execution boundaries; catalog membership does not bypass any independent control.

## Public protocols.json

`frontend/public/protocols.json` is served as `/protocols.json` without importing backend code into the browser or adding an unauthenticated backend API. Each chain-ID key now contains `contracts` and `sign`: `{"1":{"contracts":[{"address":"0x...","protocol":"...","abi":[...]}],"sign":[]}}`. This replaces the previous direct contract-array structure; consumers must read `catalog[chainId].contracts`. Exported addresses are lowercase. Each address/protocol pair is a separate object, so multiple protocol labels at one address are retained.

Protocol labels come from the current catalog and must use one canonical name across every function and deployment of the same protocol. In particular, use `Aave V3`, `Morpho Blue`, and `Compound III`, not their slug variants `aave-v3`, `morpho-blue`, or `compound-iii`. These slugs remain valid parts of existing capability IDs; do not rename capability IDs or change grants when correcting labels. Functions at the same chain/address now share one ABI object under the canonical protocol name. Historical evidence snapshots retain their original labels and are not current catalog inputs.

Only active chains, active contracts, and active `contract_call` functions with verified provenance are exported. No functions are discovered from full source ABIs; read-only functions appear only if already admitted as active catalog functions. An eligible function must have a protocol label; export fails rather than inventing one. Chains, addresses, protocol labels, and canonical function signatures are sorted deterministically. The function ABI retains `type`, `name`, `stateMutability`, `inputs`, `outputs`, and recursive tuple `components`; `internalType` and catalog-only metadata are omitted.

`sign` lists independently supported signing capabilities, not ABI functions. Polygon 137 exports Polymarket `ClobAuth`, CLOB V2 `TypedDataSign` (the envelope, not its inner `Order`), and DepositWallet `Batch`. Each record contains only `protocol`, the existing runtime `capabilityId`, `type: "typed_data"`, and `primaryType`. Other chains have an empty `sign` array. Signing-only Polygon is retained even if no contract calls are present. No dynamic addresses, nonce, deadline, EIP-712 types or request templates are exported; domain, wallet, payload, grant and pause validation remain mandatory. This is not a list of arbitrary message/raw-hash signing permissions. Batch signing has broad zero-native-value call authority and does not broadcast; catalog membership is not a safety guarantee.

This is static public metadata, not live authorization or pause state. It supplies no API-key grants and guarantees neither successful execution nor current deployment identity, balances, liquidity, or financial safety. In particular, an exported structured-executor ABI does not bypass runtime nested-execution scope, admitted-child bindings, child grants, pauses, or canonical-calldata controls. Those restrictions are intentionally not encoded in this minimal ABI download and remain independently enforced by runtime.
