## Grant and transaction semantics

- Grant authority is function-level and exact to chain, address, selector, and fixed ABI. A grant permits caller-chosen ABI arguments: assets, amounts, recipients, native value when the ABI is payable, borrow amount, minimum output, deadline, and other ABI parameters are not constrained by former platform financial caps or action templates. Protocol contracts retain their own revert/validation semantics.
- `approve(address,uint256)` is a separately and explicitly grantable function. Any spender and any `uint256` amount, including `type(uint256).max`, are permitted by this function grant. Approval is not auto-granted with an action, has no required matching action in the same request, and has no automatic cleanup/reset. A grant is not created merely by catalog admission.
- The DAI/BTCB/ETH approval entries are independent exact-token grants; their presence does not imply that DAI is a SparkLend market or that BTCB is vBTC's underlying. The Venus deployment record gives constructor schema, not actual constructor argument values. No approval pairing or spender/amount constraint is implied.
- Existing capability IDs remain; their scope is intentionally broader under this approved model. Existing narrow grants do not receive the removed financial guardrails. Owners should review and, if the broader authority is not intended, revoke and explicitly re-grant appropriate capabilities. No schema migration is needed for this model change.
- Dashboard catalog and grant management remain IAM-only; grant edits retain step-up. The read-only `GET /v1/defi-capability-bundles` is IAM + `FrontendOnlyGuard` protected, omitted from public OpenAPI, and unavailable to API-key auth. Bundle preview does not persist: additions are unioned with current selection, and replacing saved grants requires explicit removal/confirmation through the existing step-up-protected full replacement. Unknown or paused selections remain visible until explicitly removed. Default-deny (new keys receive no catalog grants), explicit grants, live pause and grant/revocation rechecks, identity, API-key permissions, freezes, session readiness, EOA isolation, generic Calibur atomicity, destination protection, billing, simulation, idempotency, and configured spend budgets with existing UTC-period/native-wei accounting remain independent gates. Openfort TEE remains the signing custody boundary; DeFi message/typed-data signing is disabled.
- Ordinary DeFi calls may still be rejected by configured API-key spend budgets, UTC-period accounting, destination protection, or billing-debt policy. These are independent existing controls, not protocol-specific financial caps. Existing interaction/decoded-node limits and the 100-grant limit remain; select only needed grants, with no silent truncation or budget increase. An NPM multicall executes one level only: its wrapper plus at most eight exact children fits under the existing ten-node ceiling; recursive multicall and unknown children are denied. Wrapper and each selected child require independent grants and pause checks. Native value is supplied once to the outer transaction and inherited by every selected child; the existing key spending limits apply to that outer request, not as a new child budget. Token funding approvals are not included or automatic and remain separately selected. NFT permits/transfers/operator approvals and other uncataloged authority are not added; unknown functions remain denied.
- Venus vToken ABI outputs are protocol error codes, not ERC-4626 shares/assets. Generic transaction confirmation does not validate Venus business success; callers remain responsible for protocol return/event interpretation. Native vBNB has distinct payable no-argument `mint()` and `repayBorrow()` declarations; they are not the ERC-20 vToken forms.
