# DeFi capability coverage (simplified function-level model)

**Snapshot: 2026-10-04.** The model catalogs exact chain/address/function-selector/fixed-ABI capabilities and requires each API key to receive explicit grants. Current assembled production snapshot: 202 active definitions across seven supported mainnets, 179 actions and 23 separately grantable canonical `approve(address,uint256)` functions. This preserves the 108-definition prior snapshot (70 baseline + 38 additions) and adds 94 definitions (91 actions, 3 approvals): 60 SushiSwap V2, four SparkLend, 27 Venus, and three independent token approvals (Ethereum DAI, BNB BTCB, BNB ETH). Oracle Gate 1 initial attempt 1/3 passed for scoped catalog/source admission and local authorization with no material findings. Both nonblocking provenance-reference alignment notes were resolved; no material re-review was needed. Independent structural scan passed. Backend build and unit validation passed (112 suites, 2,263 tests); one opt-in PostgreSQL suite/test was skipped. These results do not prove funded live UserOperation execution or authenticated-browser verification.

## Grant and transaction semantics

- Grant authority is function-level and exact to chain, address, selector, and fixed ABI. A grant permits caller-chosen ABI arguments: assets, amounts, recipients, native value when the ABI is payable, borrow amount, minimum output, deadline, and other ABI parameters are not constrained by former platform financial caps or action templates. Protocol contracts retain their own revert/validation semantics.
- `approve(address,uint256)` is a separately and explicitly grantable function. Any spender and any `uint256` amount, including `type(uint256).max`, are permitted by this function grant. Approval is not auto-granted with an action, has no required matching action in the same request, and has no automatic cleanup/reset. A grant is not created merely by catalog admission.
- The DAI/BTCB/ETH approval entries are independent exact-token grants; their presence does not imply that DAI is a SparkLend market or that BTCB is vBTC's underlying. The Venus deployment record gives constructor schema, not actual constructor argument values. No approval pairing or spender/amount constraint is implied.
- Existing capability IDs remain; their scope is intentionally broader under this approved model. Existing narrow grants do not receive the removed financial guardrails. Owners should review and, if the broader authority is not intended, revoke and explicitly re-grant appropriate capabilities. No schema migration is needed for this model change.
- Dashboard catalog and grant management remain IAM-only; grant edits retain step-up. Public transaction submission remains API-key-only. Default-deny (new keys receive no catalog grants), explicit grants, live pause and grant/revocation rechecks, identity, API-key permissions, freezes, session readiness, EOA isolation, generic Calibur atomicity, destination protection, billing, simulation, idempotency, and configured spend budgets with existing UTC-period/native-wei accounting remain independent gates. Openfort TEE remains the signing custody boundary; DeFi message/typed-data signing is disabled.
- Ordinary DeFi calls may still be rejected by configured API-key spend budgets, UTC-period accounting, destination protection, or billing-debt policy. These are independent existing controls, not protocol-specific financial caps. Structural transaction limits and the 10-interaction/100-grant limits remain; with 202 catalog entries, clients should select only needed grants and the limit must not be raised or silently truncated. Broad executors/commands, permit, NFT, and other uncataloged authority are not added; unknown functions remain denied.
- Venus vToken ABI outputs are protocol error codes, not ERC-4626 shares/assets. Generic transaction confirmation does not validate Venus business success; callers remain responsible for protocol return/event interpretation. Native vBNB has distinct payable no-argument `mint()` and `repayBorrow()` declarations; they are not the ERC-20 vToken forms.

## Provenance and validation boundary

Admission provenance means an official address source and corresponding fixed function interface/version/date were identified. It is not a protocol safety audit, liquidity guarantee, implementation/runtime identity proof, or assurance a transaction succeeds. Only the exact cataloged address/function/ABI entries are admitted; no arbitrary deployment with a matching ABI is automatically included. Historical research artifacts and receipts retain their original pre-simplification context and must not be rewritten as evidence for the new model.

Family source admission and local authorization validation are not runtime or execution validation. Oracle Gate 1's scoped catalog/source admission and local authorization review passed, with no material findings. Both nonblocking provenance-reference alignment notes were resolved; no material re-review was needed. Independent structural scan, backend build, and unit validation passed (112 suites, 2,263 tests); one opt-in PostgreSQL suite/test was skipped. Spark's source/address-to-ABI bridge has been closed using the pinned official interface and address registry, but this is not runtime code, proxy implementation, or execution proof. Gate scope does not cover financial strategy, runtime safety, liquidity, mainnet deployment, transaction success, or authenticated-browser proof. Do not treat catalog admission as deployment/publishing approval, liquidity evidence, or proof of funded live UserOperation success. See the [research index](defi-research/README.md); historical research links and receipts retain their original scope and meaning.
