# M1 ordinary-workflow baseline (seed, not denominator)

This is an independently sourced workflow seed for the pinned DeFi catalog; it is **not** the active-market universe, a denominator, nor a claim that any product is fully supported. The machine-readable records are in [`data/defi-coverage/workflow-baseline.json`](../../data/defi-coverage/workflow-baseline.json). They preserve unknowns and distinguish function coverage at enumerated exact targets from product-wide workflow completeness.

## Snapshot identity and limits

- Catalog baseline: `0x43ec3be0b20a32457719d8edb17c8eaa40c93480921d6e7c86e9c2cacdec5897`, 202 exact definitions (179 actions, 23 canonical approvals), seven configured chain IDs. This data-only pass does not change or grant catalog authority.
- Workflow research is marked with local date `2026-10-04`; timezone and UTC capture time are unknown. No UTC time was inferred.
- The file contains 16 workflow/product seeds and 35 ordinary-workflow records. It records 44 product-assigned chain/target observations, seven explicit unknown-target placeholders, and one separate observed-but-unassigned Velodrome V2 router target. These are not counts of unique deployed addresses or complete instance populations.
- Each product `presentCapabilityIds` entry is matched mechanically by exact chain ID, target address, function name, and canonical signature against the pinned catalog. Its parallel `presentFunctionBindings` entry records those identity fields plus the existing ABI hash for independent cross-checking. This bounded seed links 172 distinct action IDs to product workflow records; seven more existing Velodrome router action IDs are retained under the unassigned-target record because the raw version mapping is unresolved. This is not evidence that each workflow is complete or that these counts form a market-coverage numerator.
- `required_functions_present_at_target` means only that each listed, signature-known function has an exact local catalog match at that target. Name-only requirements whose ABI signature is not independently established remain in `unresolvedFunctionNames`; unknown requirements use `null`. Missing requirements stay explicit and are never inferred from empty arrays.
- Every `wholeProductComplete` value is `false`. Target observations do not establish complete deployment, market, reserve, pool, gauge, vault, or NFT-manager populations.
- The separate public discovery roster remains 8,476 rows; it is not filtered, normalized, or reclassified by this file. The 90-day active-product denominator and comprehensive deployment populations remain unknown.

## Interpretation rules

1. Product identity is not inferred from protocol-name similarity. Raw market references retain `matched`, `ambiguous`, `unresolved`, or no-exact-match status independently of catalog function presence.
2. Function matches require exact chain, target, name, and signature. A present capability list documents only the functions on which it matches; unknown requirement signatures or target mappings do not count as present.
3. Aave asset arguments select protocol-native reserves; the workflow inventory does not create financial or asset restrictions. Compound supply/withdraw semantics are not rewritten as extra selectors. Venus method return codes and Lido finalization remain protocol semantics, not authorization promises.
4. ERC-20 approvals remain separately grantable for any spender and any `uint256` amount. This file creates no approval prerequisite, action pairing, automatic grant, cleanup, owner pin, price/health check, runtime-code proof, or funded-execution assertion.
5. These seeds do not establish the frozen active-protocol denominator or the overall 90-day coverage objective. Unknowns must remain in later coverage projection.
