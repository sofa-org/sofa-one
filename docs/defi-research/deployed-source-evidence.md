# Deployed-source correspondence evidence — Ethereum-first subset

Research snapshot 2026-10-02. Purpose: bridge the gap between an address/code hash and the source/interface that actually produced deployed code. This is provenance evidence, **not** permission to activate, a financial risk approval, or proof of current pool/reserve/price safety. No signing, state-changing calls, funds, private keys, dependency installation, or runtime/test files were involved.

## Method and meaning of verification

- Queried the public Sourcify v2 contract lookup, `GET https://sourcify.dev/server/v2/contract/{chainId}/{address}?fields=all`, against exact chain/address. This is Sourcify's API, not an ABI scraped from a source-link in another contract. It returned `creationMatch`, `runtimeMatch`, verified timestamp, compilation metadata, metadata/source-file hashes, transformed bytecode and (where recognized) proxy resolution. API response source files/metadata are linked below per record.
- Sourcify uses `exact_match` for an exact/full match and `match` for a partial match (see [official match semantics](https://docs.sourcify.dev/docs/exact-match-vs-match/)). `match` still asserts deployed bytecode corresponds to recompiled submitted source after permitted metadata/immutable/library transformations; it is not an exact byte-for-byte full match. Values below report the API labels literally. No source match is upgraded to `exact_match` by this note.
- Primary-source `keccak256` is the value from Sourcify metadata and independently recomputed from the returned source content where noted. Metadata SHA-256 is a locally derived stable digest of the returned metadata JSON canonicalized as sorted-key compact JSON; it is an evidence fingerprint, not a Sourcify-provided field. `matchId` is Sourcify's record ID.
- Runtime hashes/blocks cited as “RPC artifact” are the existing read-only observations in [`deployment-checks.md`](./deployment-checks.md); they are not recreated here. Sourcify deployment block is creation provenance, not the height at which current runtime code was observed. This distinction matters for proxies and mutable storage.

## Scope boundary and actual remaining blocker

This closes a concrete Ethereum-first deployed-source mapping for the deadline router, canonical WETH, Aave implementation, Calibur, and the two Chainlink feeds' proxies/aggregators; it also resolves the current Circle USDC implementation **as reported by Sourcify proxy resolution and Etherscan's verified-proxy page**. It does not certify the live current proxy storage value at a parent-selected fork block, or the verified output after that block is selected. Before any fork assertion/activation, independent same-block preflight must match: router code/runtime hash and `factory()/WETH9()`, WETH code, USDC custom ZeppelinOS implementation slot (not EIP-1967), implementation runtime, Aave Pool EIP-1967 implementation/library addresses, Calibur runtime, and feed proxy aggregator links/code/rounds. The exact public RPC call for USDC implementation must query slot `0x7050…f8c3`; a zero EIP-1967 slot is irrelevant. A missing/mismatched source/status/bytecode/constructor/library link is a fail-closed blocker. Source correspondence alone is not deployment authorization or financial approval.
