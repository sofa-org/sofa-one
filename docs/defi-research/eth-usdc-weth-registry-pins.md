## Specific schema/evidence compatibility issues for the registry writer

1. `buildReviewedManifest` currently rejects every non-candidate `ReviewedDeployment` with empty `identityChecks`; the factory and pool do not have a zero-argument identity getter implemented in `DefiEvidenceService.readIdentity`. Factory binding is instead verified through actual argument-bearing `getPool(USDC,WETH,500)` **and reverse-order** calls plus pool getters. Do not invent factory `WETH9()`. The writer must support source-reviewed `getPool` relation identity / no-getter verified deployment, or keep those rows candidate; the latter means these types/current verifier still cannot close the reviewed production mapping.
2. Pool `ReviewedPool` refs express directional input/output. Both directed policy pool rows above intentionally point to the same actual physical pool; either-direction `getPool` call returns same address. The evidence verifier already checks canonical sorted token0/token1 and action direction refs.
3. `ReviewedPriceFeed` has no aggregator field. The verified deployment row for each proxy must carry literal `identityChecks: [{getter:'aggregator()',expected:<current aggregator>}]`; a separate `feed-aggregator` deployment must be in the manifest, with Sourcify source/runtime identity/hash. `DefiEvidenceService.checkFeed` resolves it by returned address and checks its runtime hash at the same block. If current aggregator changes, resample and re-source/re-pin; do not pin stale aggregator blindly.
4. Both feed `maxAgeSeconds` values are literal current official heartbeat seconds (ETH 3600, USDC 82800), not a guarantee of timely publication. Feed docs permit a product cap `min(heartbeat + bounded grace, product staleness cap)`; no bounded grace or distinct product cap is authorized/pinned in these source records. Current evidence verifier uses `maxAgeSeconds` directly; retain fail-closed direct heartbeat unless parent accepts an explicit stricter product cap / bounded grace.
5. **Concrete missing manifest value:** `ReviewedDeployment.abiHash` is mandatory for verified rows, but neither its type nor manifest builder specifies whether it hashes canonical ABI JSON, source interface text, or another stable encoding. This lane deliberately leaves ABI hashes unmade rather than disguising source hashes as ABI hashes. The registry owner must choose/document canonical ABI serialization and compute it from the exact ABI supplied for router `exactInputSingle`, ERC20 balance/allowance/decimals, pool getters, factory `getPool`, Chainlink proxy, and aggregator functions. Source refs and actual signatures/interfaces are provided here; this is the only value-level field not responsibly fillable from the documented rules.
6. Factory and pool source status is Sourcify `match` (partial), not `exact_match`; router/proxy same. Aggregators are `exact_match`. Preserve these literal labels. No current live feed availability/price or full UserOperation success claim follows from source or RPC identity.
