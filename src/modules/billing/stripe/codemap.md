# Code Map for /src/modules/billing/stripe

## Responsibility

Server-side Stripe payment rail for SOFA ONE billing (Phase 3A + Gate 1 remediation): creates one-time Stripe Checkout sessions (`mode: 'payment'`) for finalized invoices and recurring fixed-fee subscription Checkout sessions (`mode: 'subscription'`), and applies signature-verified Stripe webhook events to local payment attempts and invoice settlement. Payment facts are **only** ever confirmed by a verified webhook — the Checkout redirect is UX only. Subscription-renewal events (`customer.subscription.*`, `invoice.*`) drive automatic renewal: they update the account's Stripe subscription mirror, deterministically materialize the local renewal invoice + fixed-fee payment attempt, and — when unmatched — are `deferred` for bounded backoff retry by the billing worker (never silently ignored). The billing worker also recovers interrupted pending Checkouts from Stripe. Stripe is an optional integration: when `STRIPE_SECRET_KEY` is not configured the client is `null`, all non-payment functionality keeps working, and Stripe callers fail closed with a 503.

### stripe-payment.service.ts

- **Responsibility**: Creates (or reuses) a Stripe Checkout session for a payable invoice — one-time `mode: 'payment'` for the full invoice total, or recurring `mode: 'subscription'` for the fixed plan fee — and, on the worker path, recovers interrupted pending Checkout sessions from Stripe. ### stripe-webhook.controller.ts

- **Symbols**: `StripeWebhookController` (`@Controller('v1/billing/webhooks')`).
- **Responsibility**: Public Stripe webhook endpoint `POST /v1/billing/webhooks/stripe`. Intentionally NOT in `openapi.yaml` and NOT behind `OpenfortUserGuard`/`FrontendOnlyGuard`/`ApiKeyAuthGuard` — Stripe signs the payload and the service verifies it from `req.rawBody` (never re-parsed). `@SkipThrottle({ short: true, medium: true })` so Stripe retries are never rate-limited.
- **Key methods**: `handleStripe(@Req() req: RawBodyRequest<Request>)` → extracts `stripe-signature` header, forwards `req.rawBody` + signature to `StripeWebhookService.handleWebhook`, always answers `{ received: true }` on success.
- **Dependencies**: `@nestjs/common`, `@nestjs/throttler` (`SkipThrottle`), `express` (`Request`), `../../../common/decorators/public.decorator` (`Public`), `./stripe-webhook.service`.

### stripe-webhook.service.ts

- **Symbols**: `StripeWebhookService` (`@Injectable`), `PaymentTransition` (type `'succeeded' | 'failed' | null`).
- **Responsibility**: Verifies the Stripe signature and applies known events atomically and idempotently. Events are idempotent on the Stripe event id: the `StripeWebhookEvent` row and the attempt/invoice updates commit in one transaction, so a processing failure rolls back and Stripe retries without a "processed but business not updated" record. Only the explicit event set is processed; unknown events are recorded as `ignored` and answered 2xx. State only moves forward: `succeeded` is never regressed by a later failure/pending event, and `paidAt` is set at most once. Renewal events additionally update the account's Stripe subscription mirror (event-order safe) and deterministically materialize exact UTC-month fixed-fee renewals; unmatched renewal events are `deferred` with bounded backoff (see Design/Patterns). Exposes `processEvent(event, lease?)` as the internal worker entry for re-applying a verified re-fetched event.
- **Constructor**: `PrismaService`, `ConfigService`, `@Inject(STRIPE_CLIENT) stripe: Stripe | null`, `InvoiceSettlementService`, `@Optional() SecurityEventService`.
- **Key methods**: `handleWebhook(rawBody, signature)` (public entry), `processEvent(event, lease?)` (worker entry), `recordIgnoredEvent`, `processKnownEvent`, `findAttemptForEvent`, `persistEventIds`, `resolveTransition`, `applySubscriptionMirror`, `materializeRenewal`, `validateRenewalReplay`, `promoteRenewalInvoice`, `bootstrapActivePlan`, `deferUnmatched`, `validateProviderFacts`, `validateAttemptIdentity`.
- **Dependencies**: `@nestjs/common` (exceptions), `@nestjs/config`, `@prisma/client` (`Prisma`), `PrismaService`, `../invoice-settlement.service` (`InvoiceSettlementService`), `../billing-json`, `../billing-period-lock`, `../../security-events/security-event.service` (`SecurityEventService`), `stripe`, `./stripe.constants`.

## Design/Patterns

- **Fail-closed optional integration**: `STRIPE_CLIENT` is `Stripe | null`; both services throw `ServiceUnavailableException` when the client or required config is missing. The app must keep working without Stripe.
- **Pinned API version**: `STRIPE_API_VERSION` is asserted to `Stripe.LatestApiVersion` and sent on every request; SDK types only reflect the latest version.
- **Server-authoritative amounts**: invoice amount/currency/ownership come from the DB; success/cancel URLs come from server config only. No client-supplied pricing.
- **Single-pending-attempt invariant**: a partial unique index `billing_payment_attempts_one_pending_per_invoice_method_idx` on `(invoice_id, method) WHERE status = 'pending'` guarantees at most one visible pending Stripe attempt per invoice (USDC pending attempts coexist on the same invoice). The index is the race-safety backbone for session creation. Charge-kind scoping extends it: a `fixed_fee` (subscription) pending attempt is never reused or released by a one-time checkout and vice versa — a mismatch is a hard conflict.
- **Deterministic idempotency keys**: `checkout:${attempt.id}` / `subscription-checkout:${attempt.id}` for session creation and `customer:${account.id}` for customer creation — a Stripe timeout/retry of the exact call returns the same object instead of duplicating it; a fresh attempt generation gets a fresh key.
- **Pending-session reuse**: a pending Stripe attempt with a persisted session id younger than the 24h TTL is reused locally (no remote fetch) only when the charge kind and amount match the request. A concurrent request that loses the insert race polls briefly (15 × 100ms) for the winner's session id; a clearly stale pending attempt (older than TTL, no session id) is released and replaced; a young legitimately-in-flight attempt is never disturbed — the caller gets a retryable `ConflictException`.
- **Atomic webhook idempotency**: the `StripeWebhookEvent` row (unique `stripeEventId`) and the attempt/invoice updates commit in one `$transaction`; a duplicate event id short-circuits as already-applied.
- **Forward-only transitions**: `succeeded` is never rewritten; failure applies only via a CAS `updateMany ... WHERE status = 'pending'` so a concurrent committed success can never be regressed; `paidAt` is set at most once and never cleared.
- **Coverage-first allocation (invoice paid last)**: `InvoiceSettlementService.settleInvoice` runs inside the webhook transaction with stable row locks (attempt → invoice order, deadlock-free) and allocates a confirmed attempt's coverage toward `BillingInvoice.allocatedMicros` (never more than the remaining balance, per-attempt idempotent via `allocatedAt`); the invoice is marked paid (`paidAt`/`paidVia`/`settlementAttemptId`) only when cumulative coverage reaches the frozen `totalMicros`. A fixed-fee recurring charge therefore allocates partial coverage on a dynamic (overage) invoice and the remainder is collected automatically by the overage worker. Any coverage/paid-marker CAS that fails to match aborts the whole caller transaction (throw → rollback) so attempt `allocatedAt` and invoice coverage/paid markers are always atomic; a genuine replay (already `allocatedAt`) is an idempotent no-op, a losing success whose invoice was settled by another attempt is `needs_review` / `duplicate_unallocated`, and a precondition failure is a no-op.
- **Dual-rail isolation**: every attempt lookup is scoped to `method = 'stripe'` (persisted object-id and metadata-attemptId lookups included), so a Stripe event can never resolve to a USDC attempt.
- **Signature verification on raw body**: `stripe.webhooks.constructEventAsync(req.rawBody, signature, webhookSecret)` — the body is never re-parsed, so the signature always covers the exact bytes received.
- **Safe failure extraction**: failure codes/messages are truncated (80/500 chars) and never include secrets or full payloads; metadata values are UUID-format-validated before any DB query so malformed/malicious metadata yields "ignored", never a 500.
- **Deferred renewal retry (bounded)**: an unmatched renewal event (`STRIPE_RENEWAL_EVENT_TYPES`) is recorded `deferred` with exponential backoff (`STRIPE_DEFERRED_BACKOFF_MS` base, hard-capped 24h) instead of silently ignored; the billing worker re-fetches it from Stripe by id and re-applies it through the same idempotent pipeline under a DB-backed retry lease (`retryOwnerId`/`retryLeaseExpiresAt`). After `STRIPE_DEFERRED_MAX_RETRIES` (5) it transitions to `needs_review` with a sanitized high-risk audit — never retried forever and never demoting a concurrently processed event.
- **Deterministic renewal materialization**: an exact UTC-month `invoice.created`/`invoice.finalized`/`invoice.paid` event may create the local renewal invoice + `fixed_fee` attempt exactly once (unique `stripeInvoiceId` mapping), but only when the account, subscription, customer, period, currency, and provider total are all proven from the account mirror and the fixed fee of the active plan version. Any other shape (dynamic overage, mid-month period, wrong amount/currency/subscription/customer, no mirror) is deferred/reviewable — never fabricated or falsely settled.
- **Subscription mirror**: `BillingAccount` carries the account's single active Stripe subscription (`stripeSubscriptionId` unique, status, period, event-order fields); subscription lifecycle events update it only when the event's subscription/customer exactly match the existing binding (first binding or same id only), and equal-second events are ordered deterministically by event id. Metadata `userId` is a locator hint only and is never trusted to bind/overwrite a mirror.
- **Checkout recovery**: the worker's `recoverPendingCheckouts` resumes interrupted pending Stripe attempts: a persisted session id is re-verified with `stripe.checkout.sessions.retrieve` (expanded `subscription`) against the local invoice/attempt identity (id, metadata, `client_reference_id`, customer, currency, amount, period, mode, subscription), and a renewal attempt with no session never creates a new one. Recovery uses `checkoutRetryCount`/`checkoutNextRetryAt`/`checkoutRetryOwnerId`/`checkoutRetryLeaseExpiresAt` leases with bounded backoff (exhaustion → `needs_review`).

## Flow

### Checkout session creation

1. `BillingController.checkoutInvoice` (`POST /v1/billing/invoices/:id/checkout`, `OpenfortUserGuard` + `FrontendOnlyGuard`) → `StripePaymentService.createCheckoutSession(userId, invoiceId)`.
2. Fail closed 503 if `STRIPE_CLIENT` is null or success/cancel URLs are unset; 404 if the account or the user-owned invoice is missing.
3. `assertCheckoutEligible`: invoice must be `finalized`, unpaid, `USD`, `totalMicros > 0`, and cent-aligned (micros % 10,000 == 0) — else 4xx.
4. Reuse path: `findReusablePendingAttempt` returns a pending Stripe attempt with persisted session id + checkout URL younger than the TTL → return `{ invoiceId, sessionId, checkoutUrl }`.
5. Otherwise `createPendingAttemptOrReuseInFlight` inserts a pending attempt (P2002 race → poll/reuse/release-stale as described above).
6. `ensureStripeCustomer` returns the account's `stripeCustomerId`, creating the Customer once with idempotency key `customer:${account.id}` and persisting it (unique column absorbs the concurrent-persist race).
7. `stripe.checkout.sessions.create` with `mode: 'payment'`, one line item (`SOFA ONE — {period} invoice`, `unit_amount` = cents), server-configured success/cancel URLs, metadata `{ invoiceId, attemptId, period }`, `payment_intent_data.metadata`, `client_reference_id: invoice.id`, and idempotency key `checkout:${attempt.id}`.
8. Persist `stripeCheckoutSessionId`, `stripePaymentIntentId`, `checkoutUrl` on the attempt; return the result. On any Stripe/DB failure, `markAttemptFailed` (pending-only CAS) releases the pending slot so future retries are not blocked, then rethrows. When the provider call may have succeeded but the local write failed, `markAttemptUnknown` keeps the attempt pending with `failureCode = local_persistence_uncertain` and schedules a worker recovery retry instead of freeing the slot.

### Subscription Checkout creation

1. `BillingController.checkoutSubscription` (`POST /v1/billing/invoices/:id/subscription-checkout`, frontend-only) → `StripePaymentService.createSubscriptionCheckout(userId, invoiceId, planVersionId)`.
2. Same 503/404/`assertCheckoutEligible` gates as one-time checkout.
3. Fail closed: `planVersion.id` must exactly equal the owned invoice's `planVersionId`, and `planVersion.monthlyFeeMicros` must be finite, positive, cent-aligned, and equal to the invoice total — a dynamic/overage invoice is rejected (a smaller recurring charge is never attached to it).
4. Reuse only a `fixed_fee` pending attempt with matching amount/currency (a `full` pending attempt is a hard conflict, never reused/released).
5. `stripe.checkout.sessions.create` with `mode: 'subscription'`, recurring monthly price at the fixed fee, `subscription_data.billing_cycle_anchor` = invoice `periodStart` (exact UTC-month contract), `proration_behavior: 'none'`, metadata `{ userId, billingAccountId, invoiceId, attemptId, planVersionId }`, and idempotency key `subscription-checkout:${attempt.id}`.
6. `persistSubscriptionCheckout` (period-lock + identity CAS) stores session/PI/subscription ids; when Stripe returns a subscription id the account mirror is bound atomically (`stripeSubscriptionId` unique) with status `incomplete`. The mirror is kept current by webhooks.

### Webhook processing

1. Stripe POSTs to `/v1/billing/webhooks/stripe`; controller passes `req.rawBody` + `stripe-signature` to `StripeWebhookService.handleWebhook`.
2. Fail closed 503 if webhook secret/client missing; 400 for missing body or signature; 400 for signature/parse failure (no side effects).
3. Unknown event type → `recordIgnoredEvent` (status `ignored`, idempotent on event id) → 2xx.
4. Known event → `processKnownEvent` in one transaction:
   a. Insert `StripeWebhookEvent` row (status `processed`); P2002 → already applied, return.
   b. `findAttemptForEvent` locates the local attempt in order: persisted object id (Checkout Session / PaymentIntent / Stripe Invoice / Subscription id) → verified metadata (`attemptId`, then `invoiceId` for the most recent pending Stripe attempt) → `client_reference_id` (Checkout only). No match → the event is `ignored` for non-renewal types or `deferred` for renewal types; a metadata identity disagreement is a `conflict` (review, no mutation).
   c. Renewal events are account-resolved by strict mirror proof (exact subscription/customer match; metadata `userId` only a hint). Fixed-fee PaymentIntent events carry `invoice` (not `subscription`): their renewal proof uses the PERSISTED account subscription mirror plus the Stripe invoice identity, never a bare PI. `customer.subscription.*` lifecycle events update the account subscription mirror (event-order safe); `invoice.created`/`finalized`/`paid` may deterministically materialize the local renewal invoice + `fixed_fee` attempt exactly once and, on `invoice.paid`, settle it. Preflight validates every provider fact (amount, currency, customer, subscription, exact UTC-month period) before any mutation; unmatched events are `deferred` with bounded backoff, never ignored.
   d. `persistEventIds` stores the actual PI/session/invoice/subscription id when the attempt was found via metadata/fallback, so later events resolve by id (out-of-order delivery converges).
   e. `resolveTransition`: `checkout.session.completed` succeeds only when `payment_status === 'paid'`; async success / `payment_intent.succeeded` / `invoice.paid` → `succeeded`; async failure / `payment_intent.payment_failed` / `payment_intent.canceled` / `invoice.payment_failed` → `failed` (SCA `requires_action`/`requires_payment_method` and canceled PIs fail closed and are never left pending forever); `payment_intent.processing` and unpaid completions → `null` (no-op).
   f. `succeeded`: mark attempt succeeded (forward-only), then `settleInvoice(tx, { id, invoiceId, method: 'stripe' })` — coverage-first allocation; a lost race to a different attempt marks this attempt `needs_review` / `duplicate_unallocated`; a fixed-fee under-charge on a larger invoice is a legitimate PARTIAL allocation (invoice stays unpaid, overage collected later) — never a fake paid. A won settlement bootstraps the account's `activeSubscriptionPlanVersionId` and persists provider ids/bookkeeping.
   g. `failed`: CAS `updateMany WHERE id AND status = 'pending'` → `failed` with truncated `last_payment_error` details; a `succeeded` attempt is never regressed.
5. Worker re-application: `BillingWorkerService.retryDeferredStripeEvents` re-fetches `deferred` events from Stripe by id and calls the internal `processEvent(event, { ownerId })` with a valid DB-backed retry lease; the pipeline verifies the lease, heartbeats it, and applies the event idempotently (status guards prevent demoting a concurrently processed event).

### Checkout recovery (worker)

1. `BillingWorkerService.tick` calls `StripePaymentService.recoverPendingCheckouts(workerId)` (bounded batch of 50).
2. Pending Stripe attempts with no persisted session (or a persisted session) and due `checkoutNextRetryAt` are claimed via the `checkoutRetry*` lease CAS.
3. With a persisted session id: `stripe.checkout.sessions.retrieve` (expanded `subscription`) must prove identity (`session.id`, metadata `{invoiceId, attemptId, period}`, `client_reference_id`, customer, currency, `amount_total`, mode, and — for subscriptions — subscription id/period). Recovery persists only proven ids; a renewal attempt with no session is never given a new Checkout session.
4. Without a session id (one-time only): a fresh `mode: 'payment'` session is created for the existing attempt (`createCheckoutForExistingAttempt`) with the deterministic idempotency key.
5. Success clears the retry lease; failures bump `checkoutNextRetryAt` (exponential, capped) and after 5 retries the attempt is `needs_review` / `checkout_recovery_exhausted`.

## Integration

- **Wired in** `src/modules/billing/billing.module.ts`: `controllers: [BillingController, StripeWebhookController, UsdcPaymentController]`; `providers` include `StripePaymentService`, `StripeWebhookService`, `stripeClientProvider`; `exports` include `StripePaymentService`. `BillingModule` imports `PrismaModule` (global `PrismaService`), `SecurityEventModule`, and `ScheduleModule.forRoot()` (for `BillingWorkerService`, which drives deferred-renewal retry and pending-Checkout recovery).
- **Entry points**: one-time Checkout via `BillingController` (`POST /v1/billing/invoices/:id/checkout`), subscription Checkout via `POST /v1/billing/invoices/:id/subscription-checkout` (both frontend-only, Openfort IAM bearer + `FrontendOnlyGuard`); the webhook endpoint is `@Public()` and throttle-skipped. The worker re-applies events through the internal `processEvent` path (never a controller/public route). None of these routes are part of `openapi.yaml` (public API-key spec).
- **Config** (`src/config/configuration.ts` → `stripe.*`): `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_SUCCESS_URL`, `STRIPE_CANCEL_URL`; the worker gate is `billing.worker.enabled` (`BILLING_WORKER_ENABLED`, default off).
- **Data model** (`prisma/schema.prisma`): `BillingAccount.stripeCustomerId` (unique) plus the subscription mirror (`stripeSubscriptionId` unique, status, period start/end, `stripeSubscriptionUpdatedAt`/`stripeSubscriptionEventId` event-order fields, `activeSubscriptionPlanVersionId`); `BillingInvoice.paidAt`/`paidVia`/`settlementAttemptId` (unique, `onDelete: SetNull`), `allocatedMicros` (cumulative confirmed coverage), and `stripeInvoiceId` (unique renewal mapping); `BillingPaymentAttempt` with unique `stripeCheckoutSessionId`/`stripePaymentIntentId`/`stripeInvoiceId`, `stripeSubscriptionId`, `stripeChargeKind` (`full` | `fixed_fee` | `overage`), `allocatedAt` (per-attempt coverage marker), `checkoutUrl`, failure fields, checkout-retry lease columns (`checkoutRetryCount`/`checkoutNextRetryAt`/`checkoutRetryOwnerId`/`checkoutRetryLeaseExpiresAt`), the partial unique pending index per (invoice, method), and the migration-only unified active-payment index (`billing_payment_attempts_one_active_payment_per_invoice_idx`) that allows at most ONE active (`pending`/`confirming`) attempt per invoice across all rails; `StripeWebhookEvent` with unique `stripeEventId`, `status` enum `processed | ignored | deferred | needs_review | failed`, and deferred-retry columns (`retryCount`, `nextRetryAt`, `errorType`, `errorCode`, `accountUserId`, `retryOwnerId`, `retryLeaseExpiresAt`).
- **Shared settlement boundary**: `InvoiceSettlementService` (sibling in `billing/`) is the single atomic settlement path shared with the USDC rail; the Stripe webhook passes its interactive transaction client.
- **Consumers**: `BillingController` (checkout + subscription-checkout routes); `BillingModule` exports `StripePaymentService` for other modules, and `BillingWorkerService` calls `StripePaymentService.recoverPendingCheckouts` and `StripeWebhookService.processEvent`. The webhook service is otherwise internal to the module.
- **Tests**: `stripe-payment.service.spec.ts`, `stripe-webhook.service.spec.ts`, `stripe-webhook.controller.spec.ts` (not part of this map).
