# DeFi registry

Registry contracts are immutable fragments of nested `chain -> contract -> function` capability data. A reviewed manifest exposes `{ chains, capabilities, manifestHash }`; `buildReviewedManifest` rejects duplicate IDs/selectors and inconsistent hierarchy/ABI, validates active identity/provenance, and deep-freezes the result. The production registry is generated from the single reviewed catalog input. Catalog definitions and profile metadata do not grant capabilities. Source admission does not prove runtime code, financial safety, market eligibility, liquidity, or funded execution. See [catalog tooling](../catalog-tooling/codemap.md); versioned research reports are historical only.

Closed multicall admission also checks the root ABI shape, finite financial vocabulary, same-chain/same-target child identity and each required ABI/execution-scope hash before freezing the graph. Scoped callback/tuple fields and fixed adapter addresses are versioned execution identity, not client overrides. Reserved Uniswap identities admit only their exact action language, explicitly bound position-manager self-multicall or closed direct-primitive scope; a generic financial wrapper or unscoped ABI cannot bypass that gate.

Merkl recipient claims, 0x NFT settlements, Umami request callbacks, Flexa preauthorized staking, Velora empty-permit settlements, Revert empty-permit lending/repayment and Napier zero-deadline collectors likewise require their dedicated exact-root/chain/signature/full-ABI scope. Manifest admission and runtime planning both reserve those identities; removing a marker or substituting a generic callback scope cannot turn them into unrestricted ordinary calls. These leaf admissions do not change existing multicall graphs or install approval/signing authority.

OpenOcean's three exact Ethereum permit-wrapper swaps also require a mandatory exact-root/full-ABI marker. Empty permit bytes must bypass the entire authority helper; invalid signatures or caught failures are not a substitute. Its ordinary route methods retain their old identities and do not implicitly grant the new selectors.

HertzFlow `createOrder` is reserved for a dedicated direct-only position-decrease scope, never the full order-creation ABI. The fixed account-derived position key, zero chosen callback/extension data and zero-native-value policy distinguish it from shared-principal ingress or oracle-parameterized atomic withdrawal. Existing finite child graphs and independently required fee provisioning are unchanged.

Registry tests follow the same domain layout: protocol-specific authorization tests live beside that protocol under `registry/<protocol>/`, cross-protocol policy integration tests live in `registry/policy-integration/`, and shared catalog/manifest test helpers live in `registry/__fixtures__/`. Test filenames describe the exercised operation or policy boundary; they do not carry temporal or release labels.

The production-registry module fixture overrides `PrismaService` directly: imported feature modules can register their own database provider, so a global mock alone does not isolate Prisma construction. Module fixtures importing the session/step-up graph also load global `ConfigModule`, matching application composition.
