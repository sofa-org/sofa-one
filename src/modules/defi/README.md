# DeFi capability operations and limitations

The current static production catalog contains **368 active exact function definitions** across seven supported chain IDs: 345 actions and 23 independently grantable canonical `approve(address,uint256)` functions. It preserves all 349 v3 definitions and adds 19 v4 source-bound functions: four Curve 3pool functions on Ethereum, nine PancakeSwap V3 Position Manager functions on BNB Chain, and six Yearn TokenizedStrategy 3.0.4 functions for one historical Ethereum instance. This is an exact function count, not protocol/market completeness or a claim of deployment/runtime verification. The earlier M2 snapshot remains 315 functions (292 actions, 23 approvals); its source and evidence are historical. See the [capability matrix](../../../docs/defi-capability-matrix.md), [M4 delivery and coverage status](../../../docs/defi-research/majority-m4-delivery.md), [M2 delivery and coverage status](../../../docs/defi-research/majority-m2-delivery.md), and the [v4 source records](../../../data/defi-catalog/v4/sources/).

Each API key must receive explicit capability-ID grants; default grants remain empty. A grant authorizes the cataloged function, while the caller controls ABI arguments—including assets, paths, amounts, recipients, referral/borrow parameters, minimums, deadlines, and payable native value. No protocol-specific financial, slippage, recipient, price, health, or amount cap is added. Curve signed coin indices and fixed three-element amount arrays, Yearn receiver/owner/maxLoss arguments, and Pancake position arguments remain caller-selected. Venus vToken and Compound V2 functions expose protocol return codes; successful EVM inclusion does not establish business-level success, and callers must interpret protocol return/event semantics. `approve(address,uint256)` is an independent grant: any spender and any `uint256` amount, including the maximum and zero, are permitted. It is never auto-granted with an action and has no matching-action, cleanup, or reset requirement. Catalog admission does not grant access. Existing capability IDs are preserved; owners should review prior grants and revoke/re-grant if they do not intend the broader scope. The 19 v4 IDs are not copied into existing API-key grants.

DeFi signing remains disabled; Openfort TEE remains the signing custody boundary. Unknown functions, ungranted capabilities, paused capabilities, and unsupported broad execution surfaces remain denied. IAM-only catalog/grant management, step-up for grant edits, API-key permissions, freezes, live pause and grant rechecks, session-key readiness, EOA isolation, and destination/billing gates remain independent controls. Generic transaction constraints and policies also remain: configured API-key spend budgets with UTC/native-wei accounting, structural limits of 10 interactions and 100 grants, Permit/Permit2 and NFT operator restrictions, destination protection, billing-debt policy, idempotency, and simulation. The 368 catalog functions exceed the existing 100-grant ceiling; clients should query/select only needed grants. The ceiling is unchanged and must not be raised or silently truncated. These separate controls may reject an otherwise granted function; they do not impose protocol-specific financial caps. No grants are automatically issued or backfilled.

Pause state is persisted in the singleton `defi_policy_state` row keyed by `global`. `DefiPauseService.setPaused(scope, paused, operator)` accepts structured `global`, chain, contract, or capability scopes and records actual changes transactionally. Pause remains an overlay on explicit grants. The database recheck cannot revoke an already signed or submitted operation.

Catalog construction validates fixed ABI identity and source/date provenance, merges family fragments, and deep-freezes the result. DeFi authorization checks exact catalog function/grant/pause state and canonical ABI decoding; it does not run separate financial templates or execution-evidence policy. Allowed events are exported after commit; denial audit follows rollback and must not mask the denial.
